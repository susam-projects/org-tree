# Org Tree

Дашборд для мониторинга орг-структуры компании: дивизионы → отделы → команды.
Интерактивное дерево и аналитическая таблица с агрегированными показателями,
работающие от собственного mock-сервера.

## Стек

React 19, TypeScript, Vite 8, styled-components 6, TanStack Query 5, zod 4,
Fastify 5, vitest 5. Монорепозиторий на npm workspaces.

UI-библиотеки не используются: вся вёрстка своя, inline-CSS нет.

## Требования

- Node.js 24 (версия зафиксирована в `.nvmrc`)
- npm 11

## Запуск

```bash
npm install
npm run dev
```

Одна команда поднимает оба приложения: API на `http://127.0.0.1:4000`
и клиент на `http://localhost:5173`. Vite проксирует `/api` на сервер,
поэтому клиент ходит на относительные пути и CORS в разработке не задействован.

Конфигурация не обязательна. Если нужно изменить порт или задержку ответа,
скопируйте `.env.example` в `.env` в корне репозитория:

| Переменная          | По умолчанию | Назначение                                                     |
| ------------------- | ------------ | -------------------------------------------------------------- |
| `HOST`              | `127.0.0.1`  | Интерфейс, на котором слушает API                              |
| `PORT`              | `4000`       | Порт API                                                       |
| `RESPONSE_DELAY_MS` | `800`        | Искусственная задержка ответа, чтобы был виден loading state   |
| `CORS_ORIGINS`      | —            | Дополнительные origin через запятую; localhost разрешён всегда |

## Структура

```
apps/api/            Fastify, отдаёт GET /api/org-tree (43 узла, три уровня)
apps/web/
  src/cache/         Слой кэширования: stale time 5 с, ревалидация по ETag
  src/orgDashboard/  Данные, агрегация, раскладка; собирает две фичи ниже
  src/orgTree/       Дерево: отображение, UI-логика, собственные UI-типы
  src/orgTable/      Таблица: то же самое для своего представления
docs/                Архитектура, модель данных, ADR
```

`orgTree` и `orgTable` не импортируют ничего за пределами своих папок —
доменные типы к ним не протекают, данные приходят пропсами. Подробности
и обоснование: [docs/architecture.md](docs/architecture.md).

## Состояние по этапам

**01 FOUNDATION** — готов, тег `step/1`.
Scaffold, абсолютные импорты, собственный сервер, валидация ответа через zod,
запрос через слой кэширования со stale time 5 секунд, интерактивное дерево,
состояния загрузки / ошибки / пустого ответа.

**02 CORE** — готов, тег не проставлен.
Split-view от 1280px с переключателем на узких экранах, таблица с суммами по
поддереву и эффективностью, взвешенной по численности, сортировка по любому
столбцу, фильтр с дебаунсом 250 мс, выделение строки подсвечивает узел в дереве.

**03 POLISH** и **04 BONUS** — не начаты.

### Известные ограничения

Перечислены честно, чтобы не выдавать их за недосмотр:

- Пока строка выделена, её ветвь в дереве не сворачивается: раскрытие предков
  выводится из выделения, а не записывается в состояние. Снятия выделения нет.
- `buildOrgTree` молча отбрасывает узлы, чей `parentId` указывает на
  несуществующего родителя. Схема валидирует узлы поштучно и связность графа
  не проверяет.
- Строки таблицы кликабельны только мышью. Клавиатурная навигация — требование
  этапа 03, там же будет сделана.
- Индикатор эффективности в дереве передаёт смысл только цветом, без текстовой
  альтернативы.

## AI в разработке

Разработка велась в паре с Claude (Claude Code) в диалоговом режиме: код писала
модель, постановка задач, архитектурные решения и приёмка — автора.
Ни один коммит не попал в репозиторий без разбора.

### Что генерировала модель

Практически весь код: сервер, компоненты, слой кэширования, агрегацию, тесты,
эту документацию. Работа шла мелкими шагами — один согласованный шаг на коммит.

### Что переписывалось и почему

Решения, где предложение модели было отклонено или исправлено:

- **Разделение на три фичи.** Модель настаивала на одной общей папке, аргументируя
  тем, что общий домен иначе останется бездомным и возникнет цикл
  `orgTree → orgDashboard → orgTree`. Автор возразил: если у дерева и таблицы
  будут **собственные** UI-типы, а дашборд станет мапить домен на них, то
  импортировать из дашборда им нечего и цикла не возникает. Это оказалось верно,
  текущая структура — результат этого возражения. См.
  [ADR 002](docs/adr/002-three-features-with-own-view-types.md).
- **Расхождение дерева и таблицы.** Автор заметил, что численность отдела в двух
  панелях не совпадает. Разбор показал, что расходятся 16 узлов из 43, а у
  четырёх отличается ещё и цвет индикатора. Модель предлагала показать в дереве
  агрегаты вместо собственных значений; выбран вариант с двумя числами.
  См. [ADR 004](docs/adr/004-aggregates-in-tree.md).
- **Сброс сортировки третьим кликом.** Модель реализовала двухтактный цикл
  строго по букве задания; расширение до трёх тактов — требование автора.
- **`useEffect` для стартового раскрытия дерева.** Модель предлагала заменить его
  на вычисление в рендере; автор оставил эффект, так как он считает значение один
  раз, а не на каждый рендер. Предупреждение линтера на этом месте — осознанное.

### Что модель нашла сама

- Мемоизация `buildOrgTree` не работала: слой кэширования возвращал новый объект
  состояния на каждый рендер, и `useMemo` пересчитывался при каждом клике.
- `@types/styled-components` версии 5 в проекте со styled-components 6, который
  везёт собственные типы.
- Схема пропускала отрицательную и дробную численность и любую строку в `updatedAt`.
- `buildOrgTree` теряет узлы при битых ссылках — воспроизведено на трёх сценариях,
  вынесено в известные ограничения.

### Как проверялось

Утверждения модели проверялись исполнением, а не на слово. Тесты прогонялись
мутационно: реализация намеренно ломалась, чтобы убедиться, что тесты краснеют.
Агрегация дополнительно сверялась с инвариантами на реальных данных, а поиск
предков — с независимым обходом цепочки `parentId` по плоскому массиву.
