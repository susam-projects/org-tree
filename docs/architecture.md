# Архитектура

## Слои

Приложение разложено на четыре слоя. Стрелки зависимостей идут только вниз:
ни один слой не знает о том, кто его использует.

```
                    App
                     │
              orgDashboard            данные, агрегация, раскладка, выделение
               │    │    │
        ┌──────┘    │    └──────┐
     orgTree     cache       orgTable   представления и слой кэширования
```

| Слой           | Отвечает за                                                       | Не знает о               |
| -------------- | ----------------------------------------------------------------- | ------------------------ |
| `cache`        | HTTP-запрос, stale time, ревалидация по ETag, WebSocket с backoff | орг-структуре            |
| `orgDashboard` | данные, сборка дерева, агрегация, патчи, раскладка, выделение     | вёрстке дерева и таблицы |
| `orgTree`      | отрисовка дерева, раскрытие ветвей, подсветка изменений           | сервере, домене, таблице |
| `orgTable`     | отрисовка таблицы, сортировка, фильтрация, клавиатура, подсветка  | сервере, домене, дереве  |

Граница между фичами не декоративная: `orgTree` и `orgTable` не импортируют
**ничего** за пределами своих папок. Проверяется одной командой:

```bash
grep -rn "from '@/" apps/web/src/orgTree apps/web/src/orgTable | grep -v "@/orgTree/\|@/orgTable/"
```

Вывод должен быть пустым. `orgDashboard` ходит в обе фичи и в кэш только через
их `index.ts`, во внутренности — никогда.

## Поток данных от API до UI

```
GET /api/org-tree                          ws  /api/org-tree/live
        │  плоский массив, ETag                    │  OrgPatchMessage
        ▼                                          ▼
conditionalGet ─── 304 ──► прежний массив   useWebSocketStream    backoff 1→30 с
        │ 200                                      │
        ▼                                          ▼
orgNodesSchema.safeParse                    orgPatchMessageSchema.safeParse
        │                                          │
        ▼  OrgNode[]                               ▼  разрыв revision → рефетч
useCachedResource      stale time 5 с       useLiveOrgUpdates
        │                                          │
        ▼  OrgTreeDataState                        ▼  OrgNodePatch[]
   dispatch({ type: 'loaded' })            dispatch({ type: 'patch' })
        │                                          │
        └──────────────┬───────────────────────────┘
                       ▼
             dashboardReducer          { tree, nodesById, aggregates }
                       │               loaded: полная пересборка
                       │               patch:  точечный пересчёт
                       │
        ┌──────────────┴──────────────┐
        ▼                             ▼
  toTreeViewNodes ──► OrgTree    toTableRows ──► OrgTable
```

Оба источника сходятся в одном редьюсере, и он отдаёт `tree` и `aggregates`
всегда вместе, одним значением. Наблюдать их рассогласованными неоткуда — это
не стилистика, а следствие ошибки, которая стоила падения на загрузке:
[ADR 006](adr/006-tree-and-aggregates-in-one-reducer.md).

Отображения `toTreeViewNodes` и `toTableRows` обёрнуты в `useMemo` по
`[tree, aggregates]`, то есть пересчитываются один раз на изменение данных.

## Почему цепочка мемоизации действительно работает

Она держится на том, что ссылка на массив данных переживает и повторные рендеры,
и ревалидацию. Обеспечивают это два механизма:

1. `conditionalGet` при ответе 304 возвращает **прежний объект**, а не парсит
   новый. Тело ответа пустое, парсить нечего.
2. `useCachedResource` оборачивает результат в `useMemo` и отдаёт один и тот же
   объект состояния, пока не изменились поля запроса.

Второй пункт появился как исправление: изначально хук создавал литерал
`{ status, data }` на каждый рендер, и `useMemo` ниже по течению пересчитывался
при каждом клике, хотя данные не менялись. Сохранённая ссылка на `data` при этом
никуда не доходила.

Дополнительно TanStack Query применяет структурное разделение: если ответ 200
содержит структурно те же данные, ссылка тоже сохраняется. То есть ETag экономит
трафик и разбор JSON, но идентичность держалась бы и без него.

С появлением живых обновлений у этой цепочки сменился потребитель: сохранённую
ссылку читает теперь не `useMemo`, а эффект, диспатчащий `loaded`. Смысл тот же,
но следствие жёстче — ревалидация, не принёсшая изменений, не приводит к полной
пересборке дерева и агрегатов вообще. А вот патч, наоборот, ссылку на дерево
меняет намеренно: иначе представления не пересчитались бы и новые значения не
доехали бы до экрана.

## Слой кэширования

`src/cache` — универсальный и о домене ничего не знает. Наружу выставлены
`CacheProvider`, `useCachedResource`, `useWebSocketStream`, `STALE_TIME_MS` и три
типа. TanStack Query внутри и за границу почти не протекает: `useQueryClient`
понадобился в `orgDashboard` ради рефетча при пропуске `revision`, остальные
импорты `@tanstack/react-query` — внутри `src/cache`.

Фича описывает свой ресурс декларативно:

```ts
const orgTreeResource: CachedResource<OrgNode[]> = {
  key: ['org-tree'],
  url: '/api/org-tree',
  parse: (json) => {
    /* валидация, бросок при неудаче */
  },
};
```

Отмена запроса при размонтировании отдельного кода не требует, но работает не
сама собой: `queryFn` обязан **прочитать** `signal`. В TanStack Query это геттер,
который взводит внутренний флаг `abortSignalConsumed`; только тогда уход
последнего наблюдателя отменяет запрос. Не прокинь мы `signal` в `fetch` —
требование молча не выполнялось бы.

`useWebSocketStream` — второй способ получить данные и тоже без знания о домене:
на вход URL, разбор сообщения и обработчик, на выход — статус соединения.
Переподключение с экспоненциальным backoff (1 с, удвоение, потолок 30 с, сброс
при успешном открытии) живёт здесь же. Обработчик и парсер хранятся в ref,
обновляемых эффектом, поэтому соединение не пересоздаётся на каждый рендер
вызывающего компонента, а сообщение всегда обрабатывает свежее замыкание.

## Живые обновления

```
orgDashboard/api/useLiveOrgUpdates    контракт патча, проверка непрерывности
        │
        ├─ revision == ожидаемого + 1 ──► onPatch → dispatch({ type: 'patch' })
        └─ разрыв ─────────────────────► refetchQueries → dispatch({ 'loaded' })
```

Логика разнесена по ответственности: `cache` держит соединение и ничего не знает
о содержимом сообщений, `useLiveOrgUpdates` понимает контракт и следит за
непрерывностью `revision`, а редьюсер дашборда применяет изменения к состоянию.

Разрыв нумерации намеренно **не** доходит до редьюсера отдельным действием: хук
просто не зовёт `onPatch` и запрашивает данные заново, а дальше обычный путь
`loaded` пересобирает всё с нуля. Отдельной ветки восстановления не появилось.

Подсветка изменившихся ячеек не участвует в этом потоке вовсе: фичи определяют
изменение сами, сравнивая значение с предыдущим отрисованным
([ADR 007](adr/007-fade-out-detected-by-the-cell.md)).

## Состояние и где оно живёт

| Состояние                | Где                         | Почему там                                   |
| ------------------------ | --------------------------- | -------------------------------------------- |
| Ответ сервера            | `cache`                     | общий ресурс, не принадлежит представлению   |
| Дерево и агрегаты        | `orgDashboard`, редьюсер    | меняются только вместе, см. ADR 006          |
| Ожидаемый `revision`     | `orgDashboard`, ref         | счётчик потока, рендер от него не зависит    |
| Статус соединения        | `cache`                     | свойство транспорта, а не данных             |
| Выделенный узел          | `orgDashboard`              | общий для двух представлений                 |
| Раскрытые ветви          | `orgTree`                   | UI-логика дерева, наружу не нужна            |
| Сортировка и фильтр      | `orgTable`                  | UI-логика таблицы, наружу не нужна           |
| Строка под фокусом       | `orgTable`                  | roving tabindex — деталь клавиатуры таблицы  |
| Подсветка изменения      | ячейка `orgTree`/`orgTable` | выводится из собственного значения ячейки    |
| Активная панель (< 1280) | `orgDashboard`              | относится к раскладке, а не к представлениям |

Выделение живёт в дашборде, потому что порождается в таблице, а потребляется
деревом. Раскрытие ветвей при этом наружу не поднято: дерево само домешивает
предков выделенного узла к своему набору раскрытых. Плата за это описана в
[известных ограничениях](../README.md#известные-ограничения).

Ожидаемый `revision` держится в ref, а не в состоянии, сознательно: его изменение
не должно вызывать рендер — на экране он никак не отражается.

## Раскладка

Split-view и переключатель разведены медиазапросами, без `matchMedia` и без
измерения ширины в JS. Ниже 1280px панель показывает только активное
представление; на 1280px и выше медиазапрос возвращает `display: block` обеим,
а переключатель скрывается.

Состояние `view` существует всегда, но выше порога ни на что не влияет, поэтому
рассинхрона между состоянием и видимым быть не может. Обоснование:
[ADR 003](adr/003-split-view-via-css.md).

## Анимации и клавиатура

Три места, где поведение задаётся не логикой, а платформой:

- **Раскрытие ветви** анимируется переходом `grid-template-rows` между `0fr` и
  `1fr` — так высота едет к «авто» без измерения в JS. Плата: дети свёрнутой
  ветви остаются в DOM, поэтому на внутреннюю обёртку вешается `inert`, иначе Tab
  попадал бы в невидимые строки.
- **Затухание ячейки** — одна CSS-анимация от цвета подсветки к прозрачному,
  включаемая на 1,5 с флагом из хука.
- **Клавиатура в таблице** — roving tabindex: `tabIndex` равен нулю ровно у одной
  строки, остальные `-1`, обработчик висит на `tbody`. Фокус переставляется
  императивно прямо в обработчике клавиши, а не через эффект: иначе он прыгал бы
  при монтировании и на каждом патче.

Каждая анимация отключается в `@media (prefers-reduced-motion: reduce)`.

## Тесты

Чистые функции покрыты юнит-тестами (`vitest`, 46 тестов в 7 файлах): агрегация
полная и точечная, состояние дашборда, сортировка, фильтрация, цикл переключения
сортировки, поиск предков. Компоненты не тестируются — `@testing-library/react` в
проект не вводился.

Тесты проверялись мутационно: реализация намеренно ломалась, чтобы убедиться,
что тесты это ловят. Замеры на текущем наборе: снять взвешивание по численности —
6 упавших тестов, заменить `Intl.Collator` на оператор `<` — один, перестать
подниматься к предкам при точечном пересчёте — четыре.

Отдельно закреплён инвариант, нарушение которого уже приводило к падению: у
каждого узла дерева есть агрегат — и после загрузки, и после патча
([ADR 006](adr/006-tree-and-aggregates-in-one-reducer.md)).

Непокрытыми осознанно остались `buildTree`, `toTableRows`, `toTreeViewNodes`,
`format` и `performanceColor`. Из них `buildTree` — единственный, где это
действительно рискованно; см. известные ограничения.

Всё, что живёт в компонентах — клавиатура, подсветка, анимация раскрытия,
индикатор соединения, — проверялось вручную в браузере. Автоматической проверки
на это нет, и это осознанный пробел, а не оплошность.
