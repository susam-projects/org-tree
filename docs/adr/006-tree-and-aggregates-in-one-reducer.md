# 006. Дерево и агрегаты живут в одном редьюсере

## Контекст

До live-обновлений агрегаты были чистой производной от дерева:

```ts
const tree = useMemo(() => buildOrgTree(state.data), [state]);
const aggregates = useMemo(() => aggregateOrgTree(tree), [tree]);
```

Живые обновления это сломали. Задание требует пересчитывать агрегаты **только для
затронутого узла и его предков**, а `useMemo` для этого непригоден: он видит два
дерева и не знает, чем они отличаются. Значит, агрегаты обязаны обновляться от
события «пришёл патч», а не выводиться из очередного дерева.

Первая реализация держала агрегаты в `useState`, пересчитывала их целиком в
`useEffect` по изменению дерева и пропускала этот пересчёт через ref-флаг, если
патч уже обновил их точечно.

**Она падала на первой же загрузке.** `tree` вычисляется `useMemo` во время
рендера, а эффект, заполняющий `aggregates`, выполняется после коммита. На
переходе `loading → success` существует рендер, где дерево уже полное (43 узла),
а агрегаты — ещё пустая `Map` из начального состояния. `toTreeViewNodes` бросает
исключение на первом же узле: для каждого узла ему нужен агрегат.

Поймано в браузере автором, а не типами и не тестами: по отдельности оба
значения корректны, некорректно только их сочетание.

## Рассмотренные варианты

**Два состояния, синхронизированные эффектом** — то, что упало. Отставание на
рендер здесь структурное, а не следствие неудачного порядка вызовов: эффект по
определению выполняется после коммита того рендера, который его породил.

**Правка состояния во время рендера.** Сравнивать текущее дерево с предыдущим,
хранимым в состоянии, и вызывать `setState` прямо в теле компонента — приём,
который React прямо разрешает, и отставание он снимает. Но сигнал «этот патч уже
посчитан, полный пересчёт пропустить» всё равно пришлось бы читать и сбрасывать
из ref во время рендера, а StrictMode вызывает тело компонента дважды: первый
проход потребил бы флаг, второй ушёл бы не в ту ветку. Вариант корректен ровно до
первого лишнего рендера.

**Сопоставление по идентичности объекта.** Запомнить, для какого дерева
посчитаны точечно обновлённые агрегаты, и использовать их, пока `tree` — тот же
объект. Не работает: `buildOrgTree` на каждом вызове создаёт новые объекты узлов,
поэтому после любого изменения дерево — другой объект, независимо от причины.
Идентичность не отличает «это следствие моего патча» от «это пришёл рефетч».

## Решение

Один `useReducer` с состоянием `{ tree, nodesById, aggregates }` и двумя
действиями:

- `loaded` — полная пересборка из плоского массива (загрузка, ревалидация,
  рефетч после пропуска `revision`);
- `patch` — записать пришедшие собственные значения узлов и обновить агрегаты
  точечно через `updateAggregatesForPatch`.

Оба действия отдают новую пару за один вызов, поэтому наблюдать её
наполовину обновлённой неоткуда.

## Последствия

**Хорошее.** Инвариант «у каждого узла дерева есть агрегат» держится
конструктивно, и на него есть отдельный тест — тот самый случай, который падал.
Отставание на рендер от кэша перестало быть опасным: отстаёт теперь целостная
пара, а не половина состояния, поэтому диспатч `loaded` спокойно живёт в обычном
эффекте.

**Цена.** В ветке `patch` редьюсер записывает новые собственные значения прямо в
существующие объекты узлов, а не пересобирает дерево. Это мутация предыдущего
состояния, против которой документация React предостерегает. Здесь она безопасна
по двум конкретным причинам: присваивания абсолютные, а не инкрементальные,
поэтому двойной вызов редьюсера в StrictMode кладёт те же значения второй раз; и
за пределами редьюсера никто не держит эти объекты, чтобы сравнивать их по
ссылке. Перестанет выполняться любое из двух — решение нужно пересматривать.

**Побочное.** Патч больше не проходит через кэш TanStack Query — вызов
`setQueryData` стал не нужен и убран. Сырой кэш теперь хранит то, что вернул
последний `GET`, а не то, что на экране; сходятся они при следующей ревалидации.
Вынесено в [известные ограничения](../../README.md#известные-ограничения).
