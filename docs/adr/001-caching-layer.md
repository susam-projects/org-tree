# 001. Кэширование: TanStack Query за собственным фасадом, ревалидация по ETag

## Контекст

Задание требует двух вещей, которые звучат похоже, но решаются разными
механизмами:

- «Запрос через слой кэширования, stale time 5 секунд»;
- «Инвалидация кэша только при реальном изменении данных».

Первое — про то, **когда переспрашивать** сервер. Второе — про то, **как понять,
что переспрашивать было незачем**. Никакая настройка stale time второго не даёт:
по истечении пяти секунд клиент обязан сходить на сервер, и без участия сервера
он не может отличить «данные те же» от «данные новые».

Значит, участие сервера обязательно, и вопрос сводится к тому, каким механизмом
его обеспечить и что взять для самого кэша.

## Рассмотренные варианты

**Собственный слой кэширования целиком.** Полный контроль, ноль зависимостей.
Но здесь легко получить тонкие ошибки: гонки параллельных запросов,
дедупликация, отмена при размонтировании, поведение при возврате на вкладку.
Всё это пришлось бы писать и тестировать самостоятельно ради задачи, которая не
является предметом задания.

**Service Worker со stale-while-revalidate.** Семантика на первый взгляд та же,
но механизм другой: воркер кэширует HTTP-ответы в отдельном потоке. Идентичность
JS-объектов он не сохраняет — `response.json()` каждый раз создаёт новые объекты,
и мемоизация в React рушится. Вдобавок воркер не перехватывает WebSocket, то есть
на этапе 03 оказался бы бесполезен. Отвергнут.

**TanStack Query.** Перечисленные тонкости уже решены и покрыты тестами
библиотеки. Минус — библиотека протекает в код фич, и «слой кэширования» из
требования превращается в «мы используем библиотеку».

## Решение

Взят TanStack Query, но спрятан за собственным фасадом `src/cache`, а
ревалидация сделана условными запросами по ETag.

Наружу выставлены `CacheProvider`, `useCachedResource`, `STALE_TIME_MS` и два
типа. Импорты `@tanstack/react-query` есть ровно в трёх файлах, все внутри
`src/cache`. Фича описывает ресурс декларативно — ключ, URL и функция разбора —
и получает состояние в виде размеченного объединения `loading | error | success`,
без `isLoading`, `isFetching` и прочей терминологии библиотеки.

Сервер отдаёт `ETag` (через `@fastify/etag`), клиент присылает `If-None-Match`.
На `304` `conditionalGet` возвращает **прежний объект по ссылке**, ничего не
разбирая: тело ответа пустое.

На `fetch` выставлен `cache: 'no-store'` — иначе HTTP-кэш браузера обслужил бы
запрос сам, и код приложения никогда не увидел бы ни `304`, ни возможности
сохранить ссылку.

## Последствия

**Хорошее.** Требование про инвалидацию выполняется буквально: при неизменных
данных по сети идёт пустой `304`, разбор JSON не выполняется, а ссылка на массив
сохраняется, поэтому вся цепочка `useMemo` ниже не пересчитывается. Замена
библиотеки затрагивает три файла и ни одной фичи.

**Цена.** Фасад — это лишний уровень косвенности, и часть возможностей библиотеки
через него недоступна: инвалидация по ключу, оптимистичные обновления,
пагинация. Понадобятся — придётся расширять интерфейс осознанно, а не
дотягиваться до `useQuery` из фичи.

**Неочевидное.** Отмена запроса при размонтировании работает только потому, что
`queryFn` читает `signal`. В TanStack Query это геттер, взводящий внутренний
флаг `abortSignalConsumed`; без обращения к нему уход последнего наблюдателя
запрос не отменяет. То есть требование «корректная отмена запросов» выполняется
побочным эффектом прокидывания `signal` в `fetch`, и при рефакторинге это легко
сломать, не заметив.

**Обнаружено позже.** TanStack Query применяет структурное разделение: если
ответ `200` содержит структурно те же данные, ссылка тоже сохраняется. Проверено
запуском `query-core` напрямую. То есть ETag экономит трафик и разбор, но
идентичность объектов держалась бы и без него — на неё завязываться как на
единственный механизм не стоит.

**Граница протекла на этапе 03.** Восстановление после пропуска `revision`
требует перезапросить ресурс, а в фасаде такой возможности нет, и
`useLiveOrgUpdates` берёт `useQueryClient` напрямую. Утверждение «импорты
библиотеки есть ровно в трёх файлах, все внутри `src/cache`» больше не
выполняется: их четыре, и один — в `orgDashboard`. Чинится добавлением рефетча в
интерфейс фасада; пока зафиксировано как есть, чтобы не выдавать нарушенный
инвариант за соблюдённый.
