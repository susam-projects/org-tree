# 002. Три фичи с собственными UI-типами

## Контекст

С появлением аналитической таблицы весь код орг-структуры лежал в одной папке
`src/orgTree`: там же оказались доменные типы, запрос данных, сборка дерева,
компоненты дерева и компоненты таблицы. Имя папки перестало описывать
содержимое, а дерево с таблицей смешались.

Требовалось разложить это так, чтобы граница между представлениями была
осмысленной, а не только по именам файлов.

## Рассмотренные варианты

**Одна общая фича** (`src/org`) с подпапками `components/OrgTree`,
`components/OrgTable`, `components/OrgDashboard` и общими `types`, `api`,
`utils`. Минимум движения, общий домен лежит в одном месте.

**Три фичи, общий домен в дашборде.** Выглядит правильнее, но при наивной
реализации даёт кольцо: если `OrgNode` и `OrgTreeNode` лежат в `orgDashboard`,
то `orgTree` и `orgTable` импортируют типы из той самой фичи, которая их же и
собирает. На рантайме цикла нет — `import type` стирается, — но концептуально
это кольцо, и лечится оно только четвёртой, «общей» папкой, то есть четырьмя
каталогами на один домен.

**Четыре каталога** с выделенным общим слоем. Честно, но избыточно для проекта
такого размера.

## Решение

Три фичи — `orgTree`, `orgTable`, `orgDashboard`, — где **каждое представление
объявляет собственный UI-тип**, а дашборд мапит на них доменное дерево.

Именно это снимает проблему кольца, из-за которой второй вариант казался
несостоятельным: дереву не нужен `OrgNode`, ему нужен свой `OrgTreeViewNode`,
объявленный у него же. Импортировать из дашборда нечего, и зависимость остаётся
строго однонаправленной.

```
orgDashboard ──► orgTree     (компонент и его UI-тип, через index.ts)
             ──► orgTable    (то же самое)
             ──► cache
```

`orgTree` и `orgTable` не импортируют ничего за пределами своих папок.

Каждая фича выставляет наружу `index.ts`; обращений во внутренности нет.

## Последствия

**Хорошее.** Границы проверяются механически, одним `grep`, а не поддерживаются
договорённостью. UI-типы заметно уже доменного: в `OrgTreeViewNode` нет ни
`budget`, ни `updatedAt`, ни `parentId` — дерево физически не может начать их
отображать, не изменив контракт. Каждое представление переносимо: его можно
забрать в другое приложение вместе с папкой.

**Цена.** Появился слой мапперов (`toTreeViewNodes`, `toTableRows`), который
копирует дерево в другую форму. Для 43 узлов это несущественно и мемоизировано,
но при большом объёме данных двойное копирование пришлось бы пересматривать.
Добавление поля в представление теперь требует правки в двух местах: в UI-типе
фичи и в маппере.

**Побочное.** Мапперы оказались удобной точкой для подмены данных: когда
понадобилось показать в дереве агрегаты вместо собственных значений узла,
изменился только маппер, а компоненты дерева — нет.

**Замечание к истории.** Этот вариант был предложен автором в ответ на возражение
модели о неизбежном кольце. Возражение было верным для варианта с общим доменным
типом и неверным в целом — разделение UI-типов его устраняет.
