# Модель данных

## Контракт API

`GET /api/org-tree` возвращает плоский массив узлов. Ответ сопровождается
заголовком `ETag`; на запрос с `If-None-Match` сервер отвечает `304` без тела.
Вместе с телом отдаётся `X-Org-Revision` — текущий номер ревизии данных, общий с
потоком патчей (см. «Контракт патча» ниже).

```ts
interface OrgNode {
  id: string;
  name: string;
  parentId: string | null; // null только у корней
  headcount: number; // собственная численность узла, без потомков
  budget: number; // собственный бюджет узла, в рублях
  performance: number; // 0–100
  updatedAt: string; // ISO 8601 с указанием зоны
}
```

Текущий набор данных: 43 узла, три уровня — 4 дивизиона, 12 отделов, 27 команд.
Состав фиксирован, а значения живут: генератор на сервере раз в несколько секунд
меняет собственные показатели 1–3 случайных узлов
([ADR 005](adr/005-websocket-and-in-process-generator.md)).

Ключевое свойство, которое легко упустить: `headcount` и `budget` — **собственные**
значения узла, а не суммы по поддереву. У дивизиона «Технологии» `headcount` равен
6 — это управленческий состав самого дивизиона, тогда как во всём поддереве 84
человека. Всё, что показывается как «всего», считается на клиенте.

## Валидация

Схема описана через zod и является единственным источником истины: тип `OrgNode`
выводится из неё через `z.infer`, отдельного руками написанного интерфейса нет.

```ts
export const orgNodeSchema = z.object({
  id: z.string().min(1),
  name: z.string().min(1),
  parentId: z.string().min(1).nullable(),
  headcount: z.number().int().nonnegative(),
  budget: z.number().int().nonnegative(),
  performance: z.number().min(0).max(100),
  updatedAt: z.iso.datetime(),
});
```

Невалидный ответ — ошибка: `parse` бросает исключение, кэш переводит ресурс в
состояние `error`, и UI показывает сообщение вместо данных. Подробности разбора
(`z.prettifyError`) уходят в консоль, а сам `ZodError` прикрепляется к исключению
через `cause`; пользователю показывается обобщённый текст.

**Границы проверки.** Схема валидирует узлы поштучно и ничего не знает о
связности графа. Ответ, где `parentId` указывает на несуществующий узел, где
идентификаторы повторяются или где ссылки образуют цикл, проходит валидацию
успешно. Последствия — в разделе о сборке дерева.

## Сборка дерева

`buildOrgTree` превращает плоский массив в лес за два прохода: первый заводит
узлы в `Map` по идентификатору, второй расставляет детей по родителям.
Узел с `parentId === null` становится корнем.

```ts
export interface OrgTreeNode extends OrgNode {
  children: OrgTreeNode[];
}
```

Сложность линейная, порядок детей соответствует порядку в исходном массиве.

**Известное поведение при битых данных.** Если родитель не найден, узел просто
не попадает никуда — ни в дерево, ни в таблицу, ни в агрегаты, и предупреждения
не будет. Проверено:

| Вход                              | Узлов на входе | Строк в таблице |
| --------------------------------- | -------------- | --------------- |
| `parentId` на несуществующий узел | 2              | 1               |
| цикл `a → b → a`                  | 3              | 1               |
| два узла с одинаковым `id`        | 2              | 1 корень        |

Это осознанно зафиксировано как ограничение, а не исправлено: сервер свой и такие
данные не отдаёт. При работе с чужим API сюда нужен явный разбор с логированием.

## Агрегация

Требование: суммарные показатели включают сам узел и всех его потомков, а средняя
эффективность взвешивается по численности.

### Формулы

Для узла `v` с множеством потомков `D(v)`, включая сам `v`:

```
totalHeadcount(v) = Σ           headcount(u)
                   u ∈ D(v)

totalBudget(v)    = Σ           budget(u)
                   u ∈ D(v)

                     Σ  performance(u) × headcount(u)
                    u ∈ D(v)
averagePerformance(v) = ───────────────────────────────
                          totalHeadcount(v)
```

Взвешивание сквозное: вклад команды в среднее по дивизиону пропорционален её
численности, независимо от того, через сколько уровней она подчинена. Это не то
же самое, что среднее по непосредственным потомкам.

При `totalHeadcount(v) = 0` возвращается `0`, а не `NaN`.

### Алгоритм

Один обход в глубину. Каждый узел возвращает родителю накопленные суммы, поэтому
поддеревья не обходятся повторно — сложность `O(n)`, а не `O(n · глубина)`.

```ts
function visit(node): Totals {
  const totals = {
    headcount: node.headcount,
    budget: node.budget,
    weightedPerformance: node.performance * node.headcount,
  };

  for (const child of node.children) {
    const childTotals = visit(child); // один раз на потомка
    totals.headcount += childTotals.headcount;
    totals.budget += childTotals.budget;
    totals.weightedPerformance += childTotals.weightedPerformance;
  }

  aggregates.set(node.id, {
    totalHeadcount: totals.headcount,
    totalBudget: totals.budget,
    averagePerformance: totals.headcount === 0 ? 0 : totals.weightedPerformance / totals.headcount,
  });

  return totals;
}
```

Результат — `Map<string, OrgAggregate>`, а не аннотированное дерево: так агрегаты
можно отдать обоим представлениям, не копируя структуру, и так их проще обновлять
точечно при патче.

Полностью функция вызывается один раз на загрузку данных — из редьюсера по
действию `loaded` ([ADR 006](adr/006-tree-and-aggregates-in-one-reducer.md)).

### Точечный пересчёт при патче

Требование этапа 03 — пересчитывать агрегаты **только для затронутого узла и его
предков**. Это возможно благодаря свойству контракта: патч никогда не меняет
структуру, только собственные значения существующих узлов. Значит, у всех
остальных узлов агрегаты остаются верными и их можно переиспользовать.

`updateAggregatesForPatch` работает так:

1. Собирает множество «грязных» узлов: сами патченные плюс все их предки, подъёмом
   по `parentId` через плоский индекс `Map<id, OrgTreeNode>`.
2. Упорядочивает их от листьев к корню, чтобы у родителя дети были уже посчитаны.
3. Для каждого считает собственные значения (у патченного узла — из патча, у
   предка — прежние, патч их не трогал) плюс агрегаты **прямых** детей из уже
   готовой карты.

Ключевое отличие от полного обхода: чужие поддеревья не обходятся вовсе — вклад
непатченной ветви берётся одним чтением её агрегата.

```
totalHeadcount(v) = own.headcount + Σ  totalHeadcount(child)
                                  child ∈ children(v)
```

Взвешенная сумма эффективности в `OrgAggregate` не хранится, но восстанавливается
из него обратной операцией:

```
weightedPerformance(u) = averagePerformance(u) × totalHeadcount(u)
```

Поэтому четвёртое поле в `OrgAggregate` не понадобилось. В точной арифметике
равенство строгое: `averagePerformance` получено делением на ту же величину, а
округление живёт только в форматировании.

**Но арифметика не точная.** В IEEE 754 `(a / b) × b` не обязано в точности
равняться `a`, а при патче предки считаются уже от восстановленных значений, то
есть погрешность может копиться от обновления к обновлению. Измерено: 5000
патчей по 1–3 случайных узла, после каждого — сверка всей карты с полным
пересчётом.

```
патчей: 5000, узлов: 43
максимальное расхождение с полным пересчётом: 2.8e-14
```

Это на десять порядков меньше, чем десятая доля процента, до которой значение
округляется при выводе. Суммы численности и бюджета не страдают вовсе: они целые
и в double складываются точно.

Сложность — `O(глубина × ветвление)` вместо `O(n)`: на текущих данных это единицы
записей из 43.

Корректность проверяется в том числе сверкой с полным пересчётом: тест применяет
патч точечно, затем те же значения — к дереву, и требует совпадения результатов.

### Проверка на реальных данных

Помимо юнит-тестов агрегация сверяется с инвариантами: сумма по корням совпадает
с суммой по всем узлам исходного массива.

```
сумма по корням == сумма по всем 43 узлам (численность): true (351)
сумма по корням == сумма по всем 43 узлам (бюджет):      true (97 110 000)

Технологии   6 →  84 чел.   31 410 000 руб.   80,2%
Продажи      5 → 125 чел.   24 420 000 руб.   63,1%
Маркетинг    4 →  59 чел.   19 860 000 руб.   67,9%
Операции     7 →  83 чел.   21 420 000 руб.   71,8%
```

## UI-типы представлений

Домен до представлений не доходит. Дашборд мапит дерево на узкие типы, каждый из
которых объявлен в своей фиче.

```ts
// orgTree — бюджета и updatedAt здесь нет вовсе
interface OrgTreeViewNode {
  id: string;
  name: string;
  ownHeadcount: number;
  totalHeadcount: number;
  averagePerformance: number;
  children: OrgTreeViewNode[];
}

// orgTable — плоская строка, глубина вместо связей
interface OrgTableRow {
  id: string;
  name: string;
  depth: number; // 0 — дивизион, 1 — отдел, 2 — команда
  headcount: number; // агрегат
  budget: number; // агрегат
  performance: number; // взвешенное среднее
}
```

Строки таблицы идут в порядке обхода в глубину, поэтому таблица без сортировки
читается как оргструктура. Глубина остаётся числом; подпись уровня
(`Дивизион` / `Отдел` / `Команда`) — дело таблицы, потому что она же использует
глубину для отступа в столбце названия.

## Форматирование

| Величина      | Правило                                              | Пример            |
| ------------- | ---------------------------------------------------- | ----------------- |
| Бюджет        | `Intl.NumberFormat('ru-RU')` + ` руб.`               | `12 345 678 руб.` |
| Эффективность | до одного знака после запятой, разделитель — запятая | `82,4%`           |
| Численность   | `Intl.NumberFormat('ru-RU')`                         | `125`             |

Разделитель разрядов — неразрывный пробел U+00A0, так что число не рвётся при
переносе строки.

Сортировка названий использует `Intl.Collator('ru')`, а не сравнение строк
операторами: иначе «Ёлка» уходит в конец за «Январь», поскольку Ё стоит отдельно
в таблице символов.

## Контракт патча для live-обновлений

Сервер шлёт по WebSocket (`GET /api/org-tree/live`) только изменившиеся узлы, а
не полный массив:

```ts
interface OrgPatchMessage {
  type: 'patch';
  revision: number; // монотонно растёт; позволяет заметить пропуск
  nodes: OrgNodePatch[];
}

interface OrgNodePatch {
  id: string; // существующий узел
  headcount?: number;
  budget?: number;
  performance?: number;
  updatedAt: string;
}
```

Изменения структуры (добавление и удаление узлов, смена `parentId`) этим
контрактом не покрываются: при них клиент запрашивает полный массив заново.
Разделение оправдано тем, что структурные изменения редки, а точечный пересчёт
для них всё равно невозможен. Генератор на сервере их и не производит.

Сообщение проходит такую же проверку zod, как и ответ `GET`, только своей схемой
(`orgPatchMessageSchema`). Невалидный патч логируется и отбрасывается, соединение
при этом не рвётся: одно битое сообщение не повод терять поток.

Применение патча:

1. Записать пришедшие собственные значения в узлы дерева и вернуть новую ссылку
   на корневой массив, чтобы представления пересчитались.
2. Пересчитать агрегаты **только** для затронутых узлов и их предков — см.
   «Точечный пересчёт при патче» выше.
3. Подсветить изменившиеся ячейки с затуханием ~1,5 с.

Первые два шага выполняются одним действием редьюсера, поэтому дерево и агрегаты
не могут разойтись ([ADR 006](adr/006-tree-and-aggregates-in-one-reducer.md)).
Третий шаг ничего не получает от первых двух: ячейка сама замечает, что её
значение изменилось ([ADR 007](adr/007-fade-out-detected-by-the-cell.md)).

### Как отслеживается пропуск сообщений

`revision` растёт монотонно и позволяет отличить нормальную последовательность
от пропуска после разрыва связи. Клиент принимает номер **первого полученного
сообщения** за точку отсчёта и дальше ждёт ровно `+1`. Если пришедший номер
больше ожидаемого, патч не применяется — вместо этого данные перезапрашиваются
целиком, и состояние пересобирается из ответа сервера.

Точка отсчёта берётся из самого потока, а не из ответа `GET`, и этого достаточно:
`GET` возвращает полный снимок на момент запроса, поэтому что происходило на
сервере до подключения, клиента не касается — важна только непрерывность с этого
момента. Именно поэтому сценарий «переподключились после обрыва и пропустили
несколько патчей» отрабатывает корректно: первый же номер после реконнекта
оказывается больше ожидаемого.

Сервер дополнительно отдаёт текущий номер в заголовке `X-Org-Revision` при
`GET /api/org-tree`. Клиент его сейчас не читает — см.
[известные ограничения](../README.md#известные-ограничения).
